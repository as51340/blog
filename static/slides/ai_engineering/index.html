AI Engineering

How I actually code with Claude

spec → slice → autonomous agents → review → merge

A talk about using AI to build real features in Memgraph, not toy demos. Thesis: AI is a force multiplier if you engineer the process around it. Left alone, it drifts.

Vibe coding vs. agentic engineering

Vibe coding

  • Prompt, eyeball the diff, accept, repeat
  • You are the loop — babysitting every step
  • No spec, no objective success criteria
  • Falls apart on large, real codebases
  • More people can code and build things

Agentic engineering

  • Design → PRD → issues → slices
  • The process is the loop, not you
  • Tests are the objective contract
  • Scales to bigger features and more complex code
  • Engineers are more productive, increased output, increased quality
Vibe = intuition-driven, human on every token. Agentic = invest up front in a spec and success criteria, then let agents execute against them.

The problem with the model & harness

Left unconstrained, the context/harness has predictable failure modes:

Agentic laziness

Stops early, declares victory, skips hard edge cases — "should work".

Self-preferential bias

Trusts its own output, reviews its own code kindly, won't challenge its plan.

Goal drift

Over a long run it wanders from the original intent — solves a nearby problem.

The best spec is executable — TDD. Write the failing test first: a red test is a goal the agent can't fake passing, so it anchors against laziness and drift at once. Everything else in this talk is process built around that idea.

Named up front because every later technique is a countermeasure. The strongest single one is test-driven development — the test IS the spec, and it's machine-checkable. Laziness → a red test can't be waved away. Self-preference → separate review session. Goal drift → the test pins the intent.

My pipeline

/grill-me → /write-prd → /to-issues → claude -p (subagent per slice) → review (fresh session) → merge (base branch)

Front-loaded thinking

The first three steps produce a durable artifact: a spec and a set of independently-shippable issues.

Cheap execution

Once slices exist, execution is parallel and hands-off. The expensive part is deciding what to build, not typing it.

Open question: should /write-prd be unified across the company — one shared PRD format so all agents speak the same language?

Move human effort to the front (design) and the back (review); automate the middle. The write-prd step is a candidate for company-wide standardization — a single PRD skill/template would make specs portable between teams and consistent for the agents consuming them.

Waterfall model vs. agile model

  • Waterfall means pipeline: definition, design, coding, testing and maintenance.
  • Agile means: smaller issues, smaller reviews, iterations, incremental etc.
  • The problem with agile was that it is super hard to understand all implications upfront.
  • By splitting into smaller tasks, you get to influence more changes as you build it (how, whant and what do you change => that's hard).

/grill-me — interrogate the design

Before any code, make the model relentlessly interview me about the plan — resolving every branch of the decision tree.

  • Surfaces edge cases I hadn't thought of (which failure crashes, which don't)
  • Forces decisions to be explicit instead of implicit
  • Directly fights goal drift — intent is pinned down before we start
  • With a good context, I am somewhere around 10 questions.

Not perfect: it still asks some completely obvious questions, and sometimes too many. Bring as much context as possible and think the design through up front; the more I give it, the sharper the questions.

If I can't answer the model's questions, I don't understand the feature well enough to delegate it. But grill-me is a tool, not an oracle — expect some trivially-logical questions and occasional over-asking. The leverage comes from front-loading context and thinking hard before the session, not from the tool alone. New idea is to use /wayfinder.

/write-prd & /to-issues

/write-prd — a technical PRD

Problem, solution, user stories, scope. Mostly you skim it — some argue you shouldn't read PRDs at all, since LLMs summarize them well.

Not sure if this should be on GH because how do you update it over time? Memory rule: probably expensive in terms of time (what's the granularity of change needed for the agent to go update the spec? + you're polluting the context)

/to-issues — your human touch

This is where I actually spend attention: how would I implement it? Can slices be parallelized? Should two issues merge, or one split further?

One slice = one agent, one branch, one PR, one review — small blast radius, parallelizable, each carries its own tests.

The PRD is a technical artifact you mostly skim — LLMs are good at summarizing it back. ISSU was the one feature spec deep enough to really matter, and even then gaps remained. The to-issues step is the human touch: slicing, ordering, parallelizing, merging/splitting — that's where my judgement adds value.

Launching a subagent per slice

One headless agent, scoped strictly to one issue, opens its own PR:

claude -p "Implement the vertical slice described in
  specs/read_only/issues/03-honor-across-failover.
  Read that issue file in full plus its parent PRD at
  specs/read_only/global-read-only-ha.md, then implement the slice.
  Scope yourself strictly to this issue.
  Make a separate GH branch and open PR with the current branch as the base." \
  --dangerously-skip-permissions \
  --output-format stream-json --verbose

Read issue + parent PRD (context) · scope strictly (anti-drift) · own branch + PR (reviewable unit) · skip-permissions (zero prompts).

Fresh context on purpose: Close the main planning session (noting its session ID so I can resume it later) and launch each slice as a new claude -p run — a clean context holding only the issue + PRD.

Vertical slice is a term connected to deep modules => classes that do a lot with a small interface, not "classitis" like in Java.

"Scope yourself strictly to this issue" is a deliberate anti-drift instruction. PRD = the why, issue = the what. stream-json + verbose so I can watch/collect the run. I deliberately close the main session and start the subagent fresh. I keep the main session's ID so I can log back into it later, but the coding agent gets a clean context — just the issue and its PRD — so none of the long planning conversation biases or drifts it. Practical gotcha: I also had to explicitly tell the subagent something like "Use the instructions from CLAUDE.md" — otherwise it skipped project conventions and, e.g., the GitHub CI labels weren't created (so CI never fired), branch/commit prefixes were off, etc. The headless agent doesn't reliably pick up CLAUDE.md on its own, so I name it in the prompt.

AFK vs. HITL

HITL — human in the loop

  • Approve every command, every edit
  • Chained to the keyboard
  • Hours of typing yes / no
  • Throughput = your reaction time

AFK — away from keyboard

  • Agent runs to completion unattended
  • Frees you for deep, focused work elsewhere
  • Come back to a finished PR
  • Throughput = number of agents

The real win is deep work. While the agent runs I concentrate fully on something else — no context-switching back to approve every step, no keeping the task warm in my head. Attention mgmt

Biggest quality-of-life change. HITL feels safe but it's a throughput ceiling and it's miserable. Beyond throughput, the underrated benefit is protecting deep work: I don't have to keep switching context to babysit — I can go concentrate on a hard problem while the agent grinds. Goal: make AFK safe enough — via specs, tests, scoping, review — that I trust it.

Enabling AFK: --dangerously-skip-permissions

Permissions are annoying and even a full allowlist can't guarantee silence: the cd … && … > file pattern trips a built-in guard the allowlist can't satisfy.

Enables AFK

  • Launch with the flag; agent can't self-grant it mid-session
  • Run from repo root, absolute paths, no cd chains

The name is not a joke

  • Nothing stops rm -rf, git reset --hard, force-push
  • Irreversible actions run with no confirmation
  • Reading untrusted content = prompt injection with a live shell

The right fix is a real sandbox. Run the agent inside a Docker container so an un-gated shell can't touch anything that matters. I first tried sandcastle, but it leans on the Anthropic API, is more geared to TypeScript, and pulls issues straight from GitHub — not a clean fit for this C++ flow. So I rolled my own: claude-sandbox (next slide).

Bypass mode fixes the annoyance but hands an autonomous process an un-gated shell: it can delete files, hard-reset, or push with no prompt, and is vulnerable to prompt injection. The proper answer is a containerized sandbox so the blast radius is the container, not my machine. I experimented with sandcastle but it assumes the Anthropic API, is oriented to TypeScript, and wants to pull issues from GitHub — it didn't fit our C++ workflow, so I built my own throwaway container, claude-sandbox — that's the next slide.

My sandbox: claude-sandbox

A throwaway Docker container that runs the agent with bypass mode safely — blast radius is the container, not my machine.

What it does

  • Clone REPO at INPUT_BRANCH, cut OUTPUT_BRANCH
  • Run claude -p --dangerously-skip-permissions with my prompt
  • Commit + push, then open a PR back to the input branch
  • Live stream-json feed piped through jq — I watch every tool call

Why it fits

  • Subscription, not API — uses CLAUDE_CODE_OAUTH_TOKEN, unsets ANTHROPIC_API_KEY
  • Runs as a non-root mg user inside the container
  • Disposable: --rm, nothing persists on the host
./run.sh "Fix the flaky test in tests/unit/foo and add a regression test" \
  feature/storage-allow-recovery-failure  claude/fix-flaky-foo  memgraph/memgraph

Positional args: "<prompt>" <input-branch> <output-branch> [owner/repo] (repo defaults to memgraph/memgraph). Lives under ../claude-sandbox.

This is the answer to the previous slide's problem. Four files: a Dockerfile (node:22-slim + git, gh, jq, Claude Code CLI), entrypoint.sh (the clone → branch → run → push → PR flow), run.sh (host helper), and a .claude config dir. Key design choices: it authenticates against my subscription via CLAUDE_CODE_OAUTH_TOKEN (from `claude setup-token`) and explicitly unsets ANTHROPIC_API_KEY so it can never bill the API; it runs as a non-root user; and the container is --rm disposable so the un-gated shell can't touch my host. This is what makes AFK + bypass mode actually safe, and unlike sandcastle it's not tied to the API or TypeScript and doesn't force a GitHub-issues workflow.

The catch: you can't just spawn 50 agents

Each coding agent eventually wants to build Memgraph. The build is the bottleneck:

RAM

Parallel C++ compiles blow up memory — the machine swaps or OOMs.

CPU

N agents × ninja -j oversubscribe every core; everything crawls.

Contention

Builds fight each other; wall-clock gets worse, not better.

What I actually do: keep it simple — plain claude -p, low concurrency. I don't use dynamic workflows / ultracode: they burn far too many tokens for the benefit here.

Corollary guardrail: never trigger a full memgraph build for a test-only slice — it compiles nothing new and wastes minutes + RAM.

Good talk about build problems
Naive fan-out is a trap for compiled languages — the constraint is my machine's RAM and cores during the build, and containerized sandboxes are the real answer. I deliberately avoid ultracode / dynamic workflows: the token cost isn't worth it for me. I just start claude -p and keep the number of concurrent agents low.

Tests = the objective anti-drift anchor

Tests make intent machine-checkable — the agent can't declare victory while they're red. They work best when I'm specific: "do this, this, and this — and look at this folder/file for how we write such a test."

  • Point it at an existing test as the pattern to follow
  • Spell out the cases to cover — don't leave "what to test" to the model

The nuance that bites: it will happily write a test for the old behavior, not realizing an equivalent test probably already exists. So you really do have to read the tests it wrote — and watch the logs to see how the system actually behaves — not just trust a green checkmark.

Tests are the anchor, but the agent grades its own homework: with good direction (which cases, which existing test to mirror) they're usually fine. The classic failure is it re-tests old behavior or duplicates a test that already exists. I read the tests and the logs to confirm real behavior, not just pass/fail.

Guardrails I keep in memory

  • Pull before branching — branch off fresh origin/<base>
  • Zero-prompt subagents — bypass mode; no cd && … > file
  • New gflag ⇒ config test — register in default_config.py
  • E2E registration — workloads.yaml + CMakeLists.txt
  • CI labels — attach labels, then close+reopen PR to re-fire CI
  • Branch/commit prefixes — feat/ fix/ testing/ docs/
  • No build for test-only slices
  • Minimal comments — no PR/ticket refs, no line numbers
  • No API pollution for tests
  • Check pinned dep versions — read conanfile.py first

Where they live: the agent's persistent memory — ~/.claude/projects/<project>/memory/: an index MEMORY.md plus one feedback_*.md file per rule (e.g. feedback_pull_before_branching.md). Project-wide conventions also sit in CLAUDE.md at the repo root. Each rule started as a mistake made once, then written down so every session & subagent inherits it.

Concretely: memory files under ~/.claude/projects/<project-slug>/memory/ — MEMORY.md is the index loaded every session, and each fact is its own feedback_*.md / project_*.md file. Repo conventions live in CLAUDE.md at the root, which the agent reads too. These accreted from real incidents and review comments — e.g. the stale-base branching rule exists because a subagent branched off an out-of-date base and produced a false bug report.

The good side: observe & test what it built

My time shifts to observing the system instead of writing code:

  • More hours actually exercising the feature & reasoning about correctness
  • Customer calls mean a lot because I can see how they really use the product
  • Reviews too: I build it, test it, play with it, and try to break it
  • Asking why? and what if?

--storage-allow-recovery-failure

Corrupt one tenant's durability → instance boots with that tenant defunct instead of crashing. I could reproduce corruption, watch it boot, and confirm healthy tenants kept working.

Hot & cold storage

Same story — build it, exercise it, observe the tiers behave. Verification is concrete, not vibes.

The core benefit: I lose far less time writing code, so I spend it observing and stress-testing. That makes me more useful on customer calls too — I actually see how they use the product. Reviews shift the same way: instead of reading C++ line-by-line I build it, run it, play with it, and try to break it. Defunct-tenant is a great example — you WANT to see the failure path with your own eyes; AI got me to a runnable state quickly and I did the observing.

Reviewing: a fresh session

I never let the same context that wrote the code also bless it — that's self-preferential bias.

  • Start a new session with the Memgraph skills & review agents (storage, HA, correctness, maintainability…)
  • Clean context = no attachment to the earlier plan
  • After every subagent finishes: review that slice, then merge it to the base branch

subagent done → fresh review session → MG skills + agents → merge to base

A model reviewing its own work in the same context is too kind. Fresh session + specialized review agents is the countermeasure to self-preferential bias.

Merge conflicts: /resolve-conflicts

Parallel slices merging into one base branch means conflicts are routine. I hand them to the /resolve-conflicts skill — a structured framework for merging imports, tests, lock files, config, and deleted-but-modified files.

Real run — PR #4354: mostly correct, but two issues slipped through.

The stupid one

Plain duplication — kept a block from both sides. Obvious on a read, trivial to fix, but a green build wouldn't have caught it.

The serious one

A genuinely subtle resolution — I'd have made the same call on my first try. Not a model failure so much as a genuinely hard merge that needs real understanding.

Takeaway: the skill does the mechanical 90% well, but conflict resolution is exactly where semantic intent hides — you still have to read the result, not trust the merge. The hard cases are hard for a human too.

Conflicts are unavoidable once you're merging many parallel slices into a shared base. /resolve-conflicts gives a repeatable framework (imports, tests, lockfile regen, config, deleted-vs-modified). On PR #4354 the output was mostly good but had two defects: one trivial duplication (kept both sides of a block — dumb but invisible to the compiler), and one genuinely subtle one that I admit I'd have resolved the same wrong way on a first pass. That second one is the honest point: some conflicts encode semantic intent that neither the model nor a quick human read reliably recovers — you must actually understand both branches. So the skill is leverage on the mechanical majority, not a substitute for reading the final merge.

The gap I haven't closed yet

Ideally this is fully automated: agent codes a slice → another agent reviews it → auto-merge — no human in between.

Have

  • Autonomous coding per slice
  • Fresh-session review with MG agents
  • Manual review + merge after each slice

Want

  • Code → review → merge as one pipeline
  • Human only on the final gate / conflicts
  • Not there yet — still the manual step

A natural next step: spin up a review subagent per issue (complexity permitting). Reviewing issue-by-issue is far easier than reviewing the whole base branch at once — that's more code, more context, and harder to reason about.

Review+merge is still me hitting the button after each subagent. The dream: a workflow that chains coding and reviewing agents and only escalates on disagreement. A concrete next step is a per-issue review subagent — but only where the issue is complex enough to warrant it. Reviewing per issue beats reviewing the accumulated base branch, which is far more code and much harder to reason about at once.

The real downside: we know the codebase less

If the agent writes most of it, our mental model of the code erodes over time.

Veterans

Those of us here longer already carry the model - we can still read and review.

Starting from scratch

My intuition: someone building a codebase this way from day one will find it much harder to ever truly know it because the understanding was never built.

Reviewing keeps you close to the code — but reviewing isn't the same as having designed and written it.

A genuine worry, not doomsday. For established engineers on an established codebase, AI is leverage on top of understanding we already have. Lean on it from day one and the deep intuition may never form.

AI can't replace us

The more complex features never came out right on their own — even with a good spec.

AI is a powerful amplifier of an engineer, not a substitute. What stays with us:

  • Architecture decisions
  • Cross-subsystem invariants
  • Knowing what "correct" means
  • Deciding what to build
  • The final review
Honest data point: a good spec for a hard feature still doesn't land end-to-end on its own. The load-bearing decisions stayed human — the reassuring part.
